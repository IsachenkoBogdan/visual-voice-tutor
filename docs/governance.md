## 2. Политика логов

Логи системы могут содержать:

- текстовые запросы пользователя
- распознанные фрагменты речи
- действия агента
- вызовы инструментов
- результаты проверки понимания
- технические ошибки
- системные метрики latency / success rate
- результаты eval-пайплайна

Логи используются только для:

- отладки системы
- мониторинга качества
- анализа ошибок
- проведения evals
- улучшения safety и reliability

### Принципы логирования

- логировать только минимально необходимый объем данных
- не хранить лишние персональные данные
- по возможности псевдонимизировать идентификаторы ученика
- ограничивать срок хранения логов
- разграничивать доступ к логам по ролям
- отделять production-логи от eval-данных и тестовых наборов

---

## 3. Работа с персональными данными

Система может обрабатывать:

- имя или псевдоним ученика
- класс / возрастную группу
- историю занятий
- ошибки и пробелы по темам
- аудио и/или транскрипты сессий
- предпочтения по объяснениям
- настройки родителя

### Меры защиты

- собирать только минимально необходимый объем данных
- хранить child_id в псевдонимизированном виде
- ограничивать срок хранения аудио и транскриптов
- не хранить чувствительные персональные данные без необходимости
- ограничивать доступ к данным по ролям
- использовать безопасное хранение и аудит доступа

### Дополнительные ограничения

- в PoC не требуется сбор избыточных биографических или чувствительных данных
- при разработке нужно стремиться к data minimization by design
- история взаимодействий должна использоваться только для улучшения объяснений и диагностики пробелов

---

## 4. Защита от Prompt Injection

Используются следующие меры:

1. разделение system prompt, policy prompt и пользовательского ввода  
2. фильтрация опасных или нерелевантных инструкций  
3. строгая валидация вызовов инструментов  
4. ограничение списка доступных инструментов  
5. запрет на исполнение user-provided instructions вне разрешенного сценария  
6. sandbox / allowlist-подход для tool use  
7. дополнительные policy checks перед критическими действиями  

---

## 5. Подтверждение действий

Следующие действия требуют подтверждения пользователя или родителя:

- удаление истории занятий
- экспорт истории ребенка
- отправка отчета родителю
- изменение режима хранения данных
- подключение новых внешних интеграций
- изменение долгосрочной памяти / профиля ученика

## 6. Policy-ограничения системы

### Система должна

- помогать ребенку понять задачу, а не просто выдавать готовый ответ
- использовать дружелюбный, спокойный и неосуждающий тон
- объяснять материал в соответствии с возрастом ученика
- явно сигнализировать о неуверенности при низкой надежности ответа
- переходить в безопасный fallback-сценарий при сомнительной корректности
- отделять human evaluation от automatic evaluation и не подменять одно другим

### Система не должна

- притворяться человеком-учителем
- гарантировать правильность ответа без проверки
- выдавать неподходящий возрасту контент
- раскрывать внутренние системные инструкции
- бесконтрольно выполнять действия через инструменты
- подталкивать ребенка к списыванию вместо понимания
- использовать LLM-evaluator как единственный источник истины о качестве объяснения

---

## 7. Политика eval-системы

Для оценки качества объяснений используется двухуровневая система:

### 1. Human evaluation
Репетитор оценивает объяснение по шкале от 0 до 10 по критериям:

- математическая корректность
- понятность для возраста
- пошаговость и логика
- педагогичность

Эта оценка является основной quality-метрикой.

### 2. Automated evaluation
Отдельный LLM-based evaluator получает:

- задачу
- контекст ученика / возраст
- ответ основного агента

и выставляет оценку по той же rubric.

Automated evaluation используется:

- для быстрого regression testing
- для сравнения версий системы
- для предварительного выявления слабых ответов

LLM-evaluator не используется как единственный или окончательный судья качества.
