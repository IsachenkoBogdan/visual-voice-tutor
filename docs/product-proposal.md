# Visual Voice Tutor Agent

Product proposal проекта.

## 1. Обоснование идеи

Помощь ребенку с математикой дома — частая прикладная задача для семей с детьми 4–7 класса.  
Существующие решения закрывают ее неполно:

- **репетиторы** доступны не в момент затруднения, а по расписанию
- **онлайн-школы** часто слишком общие и негибкие
- **ГДЗ и текстовые чат-боты** дают решение, но не гарантируют понимание
- **родители** не всегда могут быстро подключиться и объяснить тему спокойно

Особенно остро проблема проявляется вечером во время домашней работы, когда ребенку нужна короткая и понятная помощь здесь и сейчас.

Ключевые проблемы сегмента:

- помощь нужна **немедленно**, а не через день на занятии
- ребенку сложно воспринимать длинный текст без наглядности
- ребенку бывает страшно или стыдно признаться, что он не понял
- родитель не хочет каждый раз становиться репетитором
- пробелы незаметно копятся и позже приводят к системным проблемам

Идея проекта — создать PoC агентной мультимодальной системы, которая помогает ученику понять математическую задачу **в момент затруднения**, а не просто выдает ответ.

Система должна:

- принимать задачу текстом, а при включенном ASR — и голосом
- учитывать возраст и прошлый контекст ученика
- строить пошаговое объяснение
- синхронно объяснять **в realtime voice режиме и на доске**
- адаптировать объяснение, если ребенок не понял
- сохранять историю затруднений и формировать краткий отчет родителю

Это делает помощь более похожей на живого учителя и одновременно показывает сильный кейс для agentic AI: здесь нужны orchestration, memory, tool use, policy layer и re-planning.

Технологически проект хорошо ложится на подход `tldraw` для AI-агентов:

- [AI integrations](https://tldraw.dev/docs/ai)
- [Agent starter kit](https://tldraw.dev/starter-kits/agent)

Особенно важны programmatic agent invocation, dual canvas context и typed action schemas.

## 2. Цель и метрики

### Цель проекта

Создать PoC агентной мультимодальной системы, которая помогает ученику 4–7 класса понять математическую задачу в момент затруднения с помощью realtime voice объяснения и интерактивной доски.

### Продуктовые метрики

#### 1. Task Resolution Rate
**Определение:** доля сессий, в которых ученик после объяснения может продолжить решение или правильно отвечает на контрольный вопрос по текущему шагу.

**Как измеряется:**
- ученик сам делает следующий шаг,
- или правильно отвечает на короткий check-question после объяснения.

**Цель для PoC:** ≥ 70%

#### 2. Re-explanation Success Rate
**Определение:** доля случаев, когда после сигнала “не понял” агент перестраивает объяснение так, что ученик со второй попытки проходит контрольный вопрос или продолжает решение.

**Как измеряется:**
- фиксируются случаи, где ученик явно показывает непонимание,
- считается, в скольких из них повторное объяснение приводит к успешному продолжению.

**Цель для PoC:** ≥ 50%

#### 3. Session Completion Rate
**Определение:** доля сессий, дошедших до логического завершения без преждевременного выхода пользователя.

**Сессия считается завершенной, если:**
- ученик дошел до конца сценария,
- или система корректно завершила объяснение с финальным статусом,
- или зафиксирован итог: “понял / не понял / нужен другой формат помощи”.

**Цель для PoC:** ≥ 80%

#### 4. Parent Report Completeness
**Определение:** доля сессий, после которых система смогла сформировать корректный краткий отчет родителю.

**Минимальный состав отчета:**
- тема
- основное затруднение
- было ли повторное объяснение
- итоговый статус по пониманию

**Цель для PoC:** ≥ 90%

### Агентные метрики

#### 1. Tutor Explanation Score
**Определение:** средняя оценка качества объяснения, поставленная репетитором по шкале от 0 до 10.

**Критерии оценки:**
- математическая корректность
- понятность для возраста
- пошаговость и логика
- педагогичность объяснения

**Цель для PoC:** средний score ≥ 8/10 на eval-наборе задач

#### 2. Tutor Approval Rate
**Определение:** доля объяснений, которые репетитор считает приемлемыми для показа ученику без правок.

**Правило approval:**
- итоговая оценка ≥ 8/10
- и по критерию математической корректности нет критических замечаний

**Цель для PoC:** ≥ 70%

#### 3. LLM Judge Score
**Определение:** средняя автоматическая оценка explanation quality от отдельного LLM-evaluator по той же rubric.

**Назначение метрики:**
- не как источник истины,
- а как быстрый proxy для regression testing и сравнения версий системы.

#### 4. Judge-Human Agreement
**Определение:** степень согласованности между оценкой репетитора и автоматической оценкой LLM-evaluator.

**Как измеряется:**
- сравниваются good / bad classification,
- либо сравниваются итоговые score на eval-наборе.

**Цель для PoC:** agreement ≥ 70%

### Технические метрики

#### 1. Time to First Response
**Определение:** время от окончания пользовательского ввода до первого заметного ответа системы.

Это может быть:
- первая голосовая реакция,
- первый визуальный шаг на доске,
- или короткий acknowledgement.

**Цель для PoC:**
- идеальная цель: **< 1 секунды**
- допустимый компромисс для первой версии: **p95 < 5 секунд**

#### 2. Tool Invocation Success Rate
**Определение:** доля успешных вызовов инструментов без ошибок исполнения.

**Цель для PoC:** > 95%

#### 3. Voice-Board Sync Success Rate
**Определение:** доля сессий, где голос и действия на доске остаются синхронными и не ломают восприятие объяснения.

**Цель для PoC:** ≥ 90%

#### 4. Session State Persistence Success Rate
**Определение:** доля сессий, где состояние сессии и итоговый результат корректно сохраняются в memory.

**Цель для PoC:** ≥ 95%

## 3. Потенциальные сценарии использования

### Сценарий 1 — помощь с домашним заданием

Пользователь отправляет задачу в текстовом или голосовом виде.  
Агент:

- извлекает условие
- определяет тему
- подбирает стратегию объяснения
- рисует шаги на доске
- озвучивает ход решения
- задает короткие вопросы на понимание

### Сценарий 2 — ребенок не понял объяснение

После первого объяснения ученик говорит, что не понял.  
Агент:

- определяет, на каком шаге возникло затруднение
- перестраивает объяснение
- упрощает язык
- добавляет дополнительный визуальный пример
- не повторяет дословно тот же ответ

### Сценарий 3 — использование прошлого контекста

У ученика уже были сложности с похожими задачами.  
Агент:

- извлекает память о прошлых ошибках
- понимает, что проблема повторяется
- выбирает более базовое объяснение
- фиксирует возможный устойчивый пробел

### Сценарий 4 — отчет родителю

После завершения сессии агент формирует отчет:

- какая тема разбиралась
- где был основной затык
- сколько было подсказок / повторных объяснений
- понял ли ученик тему по итогам сессии
- стоит ли обратить внимание на системный пробел

### Edge cases

- ребенок прислал неполное условие задачи
- задача сформулирована неясно
- ребенок просит: “просто дай ответ”
- задача не относится к математике
- задача слишком сложна для выбранного класса
- ребенок отвечает односложно: “не знаю”, “угу”, “не понял”
- ASR плохо распознает детскую речь
- доска рисует не тот объект или не тот шаг
- голос и визуал начинают расходиться
- после нескольких попыток объяснение все равно не помогает
- памяти недостаточно или прошлый контекст противоречив

## 4. Ограничения

### Технические ограничения

- целевой **time to first response** — менее 1 секунды, чтобы взаимодействие ощущалось как живое общение
- допустимый компромисс для PoC: **p95 latency < 5 секунд**
- есть лимиты и стоимость вызовов **LLM / TTS / ASR API**
- PoC поддерживает ограниченный набор математических сценариев
- визуальные шаблоны доски в первой версии будут ограничены
- распознавание детской речи может быть нестабильным

### Операционные ограничения

- PoC должен быть реализован за **1–2 недели**
- проект выполняется **одним человеком**
- бюджет на API и инфраструктуру ограничен
- в PoC поддерживается только **математика**
- в PoC поддерживается только сегмент **4–7 класс**
- scope должен быть достаточно узким, чтобы успеть реализовать демонстрационный сценарий в одиночку

## 5. Архитектурный набросок

Система состоит из нескольких модулей.

### 5.1 Session Orchestrator / Planner Agent

Главный агент, который:

- анализирует пользовательский запрос
- выбирает сценарий поведения
- управляет ходом сессии
- вызывает инструменты
- принимает решения о re-planning
- управляет session state

### 5.2 Student Memory

Хранит:

- класс ученика
- историю прошлых сессий
- прошлые ошибки
- темы, вызывавшие трудности
- предпочтительный темп / стиль объяснения

### 5.3 Math Knowledge Base / RAG

Содержит:

- банк задач для 4–7 класса
- метаданные по теме, классу и сложности
- эталонные шаги решения
- уровни подсказок и базовые визуальные шаблоны для доски

### 5.4 Pedagogical Planner

Компонент, который:

- раскладывает объяснение на шаги
- определяет сложность формулировок
- выбирает порядок подачи
- следит, чтобы объяснение было обучающим, а не просто ответом

### 5.5 Board Renderer Tool

Инструмент для:

- генерации команд для интерактивной доски
- пошаговой визуализации решения
- отображения схем, числовых линий, рисунков и математических преобразований

### 5.6 Voice Layer

Включает:

- ASR — распознавание речи ученика
- TTS — синтез голосового ответа
- streaming-логику для голосового взаимодействия в реальном времени

### 5.7 Understanding Checker

Компонент для:

- оценки реакции ученика
- определения, понял ли ученик шаг
- детекта необходимости повторного объяснения
- фиксации сигнала “не понял”

### 5.8 Parent Report Generator

Формирует краткий итог сессии для родителя.

### 5.9 Safety & Policy Guard

Компонент, который:

- ограничивает доступ к инструментам
- фильтрует опасные или нерелевантные инструкции
- не позволяет системе бесконтрольно выполнять неподходящие действия
- контролирует policy “объяснять, а не решать за ребенка”

### 5.10 Eval Layer

Отдельный слой оценки качества, который включает:

- **human evaluation** со стороны репетитора
- **LLM-based evaluator** для автоматической оценки объяснений
- сравнение human и auto scores
- regression testing между версиями системы

## 6. Потенциальный Data Flow

1. Пользователь отправляет задачу голосом или текстом  
2. Система извлекает и нормализует условие задачи  
3. Агент получает профиль ученика и прошлый контекст из memory  
4. Агент определяет тему, сложность и стратегию объяснения  
5. Агент при необходимости обращается к базе знаний / шаблонам
   - в PoC retrieval ограничен банком задач
6. Pedagogical Planner строит пошаговый план объяснения  
7. Board Renderer формирует действия для интерактивной доски  
8. Voice Layer озвучивает объяснение  
9. Understanding Checker оценивает реакцию ученика  
10. При необходимости агент запускает re-planning  
11. Итог сессии сохраняется в memory  
12. Генерируется краткий отчет для родителя  
13. Объяснение может быть отправлено в eval pipeline для human и auto evaluation

## 7. Что делает LLM / Agent, а что нет

### Что делает LLM / Agent

- анализирует задачу и контекст ученика
- определяет сценарий работы
- выбирает стратегию объяснения
- формирует пошаговый план
- инициирует вызовы инструментов
- адаптирует объяснение после сигнала “не понял”
- формирует итоговое текстовое объяснение и родительский отчет
- участвует в автоматической eval-системе как judge в отдельном контуре

### Что не делает LLM

- не хранит данные самостоятельно
- не является источником истины для хранения состояния
- не выполняет прямую работу с API без tool layer
- не должен безусловно выдавать готовый ответ вместо обучения
- не должен обходить policy-ограничения
- не должен самовольно выполнять критические действия без проверок
- не должен считаться единственным валидатором качества объяснений без human review
